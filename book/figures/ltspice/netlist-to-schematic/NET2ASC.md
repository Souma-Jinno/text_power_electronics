# net2asc.py — ngspice ネットリスト → LTspice 回路図 自動生成 (v2)

`.cir` を読んで、**接続が構造的に正しい** `.asc` を出力するツール。
出力は必ずラウンドトリップ検証にかけ、PASS/FAIL を報告する。

> **ファイル名について（2026-09-04）。** この文書の 6 章・7 章・8 章は開発機で実測した
> ログである。そこに出てくる `external/rectenna_harvester.cir` /
> `external/rectenna_harvester.asc` は**作者の作業機のパス**で、
> 作者の機械では別のファイル名（未公開プロジェクトの内部呼称）で置かれている。
> 配布物に内部呼称を残さないため、**この文書中の表記はパッケージ側の名前
> `rectenna_harvester` に統一してある**（作者の作業機のファイル自体は改名していない）。
> 数値・レイアウト・PASS/FAIL といった実測内容は一切変えていない。
> パッケージに同梱しているのは `examples/rectenna_harvester.cir`（同じ回路。
> ヘッダの研究固有の記述だけを外したもの）。

  **既存のロールバック＆リトライを発火させる配置失敗**として扱い、
  全候補が駄目なら**その配置を許可したうえで数を数えて報告**する（ハードエラーにはしない）。

  監査の破壊 3 種と出荷済み負制御 2 種は 5/5 FAIL（終了コード 1）のまま。
  `buck/buck_sync.asc` は**変更前とバイト一致**（flow レイアウトは無改造）。

- 補助: `ngspice/ascnet_check2.py`（フラグ名マージ対応のネットチェッカ、新規ファイル）

## 1. 使い方

```bash
# 基本（検証は既定でON）
python3 ngspice/net2asc.py opt/variants/llc.cir -o llc_auto.asc

# ラウンドトリップ結果の .cir を明示指定
python3 ngspice/net2asc.py opt/variants/llc.cir \
        -o llc_auto.asc --rt render_test/llc_auto_rt.cir

# 検証をスキップ（非推奨）
python3 ngspice/net2asc.py foo.cir -o foo.asc --no-verify

# レイアウト調整
python3 ngspice/net2asc.py foo.cir -o foo.asc --cols 10 --stub 16
```

主なオプション

| オプション | 意味 |
|---|---|
| `-o, --output` | 出力 `.asc`（既定: 入力のベース名 + `.asc`、カレントディレクトリ） |
| `--rt` | ラウンドトリップで生成する `.cir` の出力先 |
| `--symdir` | シンボルライブラリ（既定 `ngspice/ltsym`） |
| `--layout` | `auto`（既定: v2 flow → v2b spine → v1 grid の順に試す）/ `flow`（ハーフブリッジ脚のみ, 不可なら異常終了）/ `spine`（spine+枝のみ, 不可なら異常終了）/ `grid`（v1） |
| `--v1` | `--layout grid` の別名 |
| `--spine` | `--layout spine` の別名 |
| `--check ASC` | 生成せず、既存の `.asc` を INPUT と突き合わせて検証（終了コード 0/1）。3 つの独立検査を走らせる → 3.5 節 |
| `--cols` | 配置の列数（v1 グリッドのみ。既定: ほぼ正方形になるよう自動） |
| `--stub` | ピンから伸ばすスタブ配線の長さ（既定 32、16 の倍数） |
| `--no-verify` | ラウンドトリップ検証を行わない |

**終了コード**: 検証 PASS で 0、FAIL で 1。CI に直接使える。

ネットチェッカ:

```bash
python3 ngspice/ascnet_check2.py llc_auto.asc                 # 同名FLAGをマージ（既定）
python3 ngspice/ascnet_check2.py --no-merge-flags llc_auto.asc # 旧来の挙動
python3 ngspice/ascnet_check2.py llc_auto.asc --inst S_SR1 --net rect
```

## 2. 設計方針 — なぜ「配線しない」のか

### 2.1 自動配線を捨てた理由

回路図の自動配線（オートルーティング）は難しい。そして**下手にやると、間違った接続の図が
「それらしく」出来上がってしまう**のが最悪である。線が交差しただけの箇所が繋がって見えたり、
逆に繋げたつもりの線が 1 グリッドずれて繋がっていなかったりする。これは目視では見つけにくく、
このプロジェクトは過去にまさにそこで痛い目を見ている。

そこで v1 は、**配線を一切しない**という方針を採った。

### 2.2 代わりにやっていること

```
  1. 各素子を粗いグリッド上に、固定ピッチで置く
       → 2つの素子のピン座標が絶対に衝突しないことを「算術的に」保証する
         （gen_cd_2phase.py がセルB のオフセット DY で衝突を排除したのと同じ発想）

  2. 各ピンから 1 本だけ、短いスタブ配線 (32 単位 = グリッド2目盛) を外向きに引く

  3. そのスタブの先端に  FLAG <x> <y> <ネット名>  を置く
```

LTspice は**同じ名前の FLAG（ネットラベル）を、配線なしで同一ノードとして接続する**。
したがって回路図の接続性は、ネットリストの接続性そのものになる。
**接続は「配線がうまくいったから正しい」のではなく、「構造上そうとしか書けないから正しい」。**
配線問題はラベル付け問題に還元された。

### 2.3 衝突しないことの算術的保証

`net2asc.py` の `_check_pitch()` が起動時に assert する。

- 使用シンボルのピン相対座標の範囲: x ∈ [-48, +16]、y ∈ [0, +96]
  （x=-48 は `sw` の制御ピン NC+/NC-）
- スタブ長 `STUB = 32` を足したセル内フットプリント:
  x ∈ [-80, +48]（幅 128）、y ∈ [-32, +128]（高さ 160）
- セルピッチ: `CELL_W = 320`、`CELL_H = 384`

隣のセルのフットプリントは `320 + (-80) = 240 > 48`、`384 + (-32) = 352 > 128` なので
**厳密に重ならない**。よって異なる素子が同じ座標を生むことはあり得ず、
「たまたま重なって繋がってしまった」事故が原理的に起きない。
全座標は 16 単位グリッド上（ピン座標・スタブ長・セルピッチが全て 16 の倍数）。

### 2.4 シンボル対応

| ネットリスト | シンボル | 端子順（= .asy の PIN 行順 = SpiceOrder） |
|---|---|---|
| `R` | `res`   | A, B |
| `C` | `cap`   | A, B |
| `L` | `ind`   | A, B |
| `L`（`K` 文で参照される） | `ind2` | A, B（極性ドットが明示される） |
| `D` | `diode` | +(anode), −(cathode) |
| `V` | `voltage` | +, − |
| `S` | `sw`    | A, B, NC+, NC− |

`K` 文に名前が出てくるインダクタだけ `ind2` にするのは、結合の向き（ドット端子）を
図の上で明示するため。`asc2ngspice.py` は `ind` / `ind2` を同じ `L` として読むので
ラウンドトリップには影響しない。

### 2.5 シンボルの無い素子 — TEXT ディレクティブへのフォールバック

`ltsym/` にシンボルが無い素子（B 電源、E/G/F/H 制御源、X サブサーキット呼び出し等）は
**描かない**。代わりに元の行をそのまま

```
TEXT <x> <y> Left 2 !<元のSPICE行>
```

として書き出す。これは手書きの `dist_asc_s6/improved_s6.asc` が
`Bgsr1` / `Bgsr2` / `Dsr1` / `Rsnb1` などを扱っているのと**まったく同じ方式**であり、
新しい発明ではなく既存のハウススタイルの踏襲である。

同じ扱いをするもの: `.param` / `.model` / `.options` / `.tran` / `.ic` / `.include` /
`K` 結合文、および入力デッキのタイトル行（`;` コメントとして）。

`.param` の中の ngspice 式クォート `'expr'` は LTspice 式 `{expr}` に書き換える
（トポロジーには無関係、LTspice で開けるようにするため）。

### 2.6 `.control ... .endc` は捨てる

LTspice に `.control` ブロックの概念は無いので、`.asc` には入れない。
代わりに落としたことを示すコメント TEXT 行を 1 行だけ入れる:

```
;.control ... .endc block dropped (13 lines): LTspice has no equivalent; re-add it in the ngspice deck.
```

シミュレーション後処理（`meas` 等）が必要なら ngspice デッキ側で行うこと。

## 3. ラウンドトリップ検証の仕組み

これは「おまけ」ではなく**このツールの成果物そのもの**である。既定で必ず走る。

```
input.cir --[net2asc.py]--> out.asc --[asc2ngspice.py]--> out_rt.cir
                                           ↓
                        input.cir と out_rt.cir の「トポロジー」を比較
```

### 3.1 何を比較するか

ネット名は途中で改名され得るので、名前の一致は要求しない。要求するのは
**「どの素子端子がどのネットを共有しているか」の同型性**である。具体的には:

1. 素子名の集合が完全一致すること（素子名はラウンドトリップで保存される）
2. 各素子の型文字（R/C/L/D/V/S/B/…）と端子数が一致すること
3. 入力側ネット名 → ラウンドトリップ側ネット名の**全単射 f** が存在し、
   すべての素子・すべての端子位置 i について
   `f(入力側の第i端子のネット) == ラウンドトリップ側の第i端子のネット`
   となること。グラウンド `0` は `0` に固定でシードする。

端子順（順序付きタプル）で比較しているので、D の アノード/カソード、V の +/−、
S の A/B/NC+/NC− の**入れ替わりも検出する**（単なる「触れているネットの集合」比較より厳しい）。

`K` 結合文は別枠で、**結合している素子名の組**と**結合係数**の両方を比較する
（係数は 2026-09-04 追加。それ以前は `t[1:-1]` として意図的に捨てられていた。3.8 節）。
素子の値は `SYMATTR Value` だけでなく `Value2` と `SpiceLine` の未消費キーも含む
（同じく 2026-09-04 追加。3.8 節）。

これに加えて、`.asc` が運んでいる**ディレクティブの多重集合**を入力デッキと
照合する（`.tran` / `.ic` の削除を捕まえる。3.5 節の検査 5、3.8 節）。

### 3.2 不一致の報告

不一致は 1 件ずつ具体的に印字される。例（意図的に FLAG を 1 個壊した負制御試験の実出力）:

```
VERIFY: FAIL
  MISMATCH: S_SR1.pin2: net 'rect' already mapped to 'rect' but here it is 'BOGUSNET'
```

そして終了コードは 1 になる。

### 3.3 「検証が素通ししていないこと」の確認（負制御試験）

検証器が常に PASS を返すだけの飾りでないことを、実際に確かめてある。

- `llc_auto.asc` の `rect` FLAG を **1 個だけ** `BOGUSNET` に書き換える → **FAIL**、終了コード 1
- `rect` FLAG を **全部** `BOGUSNET` に書き換える → **PASS**
  （これは正しい。全部同時に改名するのは単なるネットのリネームであり、
   トポロジーは変わっていない。仕様通りの挙動である。）

### 3.4 ラウンドトリップの再抽出器は `asc2ngspice.py`（「権威」ではない）

> **2026-08-27 改訂。** ここには以前「ラウンドトリップの**権威**は `asc2ngspice.py`」と
> 書いてあった。この言い方は**取り下げる**。独立監査（3.6 節）が示したとおり、
> `asc2ngspice.py` は LTspice の接触意味論の一部しか実装しておらず、
> 「権威」と呼んだことで**その盲点がそのまま検証全体の盲点になっていた**。
> `asc2ngspice.py` は **1 つの再抽出器（re-extractor）** であって、
> それ自体が正しさの基準ではない。検証は複数の独立した検査の合議で行う（3.5 節）。

**重要な非対称性**があるので明記する。

- `dist_asc_s6/tools_ascnet_check.py` は FLAG の座標を登録するが、
  **同名 FLAG 同士を同一ネットに union しない**。ネットは座標の union-find 根で決まり、
  FLAG 名は「その連結成分のラベル」としてしか使われない。
- 一方 `asc2ngspice.py` は FLAG 名でノード名を決めるので、**名前でマージする**
  （＝ LTspice の実際の意味論と一致する）。

net2asc.py は名前接続に全面的に依存しているので、旧チェッカで見ると
すべてのピンが 1 ピンの孤島に見える。実測:

```
ascnet_check2.py --no-merge-flags llc_auto.asc : pins=122 distinct nets=122  one-pin nets=122
ascnet_check2.py                  llc_auto.asc : pins=122 distinct nets=29   one-pin nets=0
asc2ngspice.py  経由の比較                      : 29 nets mapped, VERIFY PASS
```

これを黙って回避せず、両方の対策を取った。

- (a) **ラウンドトリップの再抽出は `asc2ngspice.py`** で行う。LTspice のネットラベル
  意味論を実装しているのはこちらであり、しかも `.cir` を実際に吐くのでトポロジー比較が
  直接できる。ただしこれは「基準（authority）」ではなく、**検査対象でもある**。
- (b) 旧チェッカは**編集せず**、新規ファイル `ngspice/ascnet_check2.py` に
  `--merge-flags`（既定 ON）/ `--no-merge-flags` を付けたものを用意した。
  上の 2 行はこのファイルで再現できる。

### 3.5 `--check` が検出する誤り / しない誤り（2026-09-04 現在）

`python3 net2asc.py INPUT.cir --check EXISTING.asc` は次の **6 つの独立した検査**を
走らせ、いずれか 1 つでも落ちれば `VERIFY: FAIL` / 終了コード 1 になる。

1. **接触検査**（`asc_contact_check`）— `.asc` の図形に対して LTspice の接触意味論で
   union-find を回し、1 つの連結成分が 2 つ以上のネット名を持っていないか見る。
2. **ラウンドトリップ**（`asc2ngspice.py` → トポロジー比較）— 素子名集合・型文字・
   端子数・ネットの全単射・**素子の値**・`K` 結合の相手**と結合係数**
   （係数は 2026-09-04 追加。3.8 節）。
   素子の値には `SYMATTR Value` だけでなく `Value2` / `SpiceLine` の
   未消費キーも含む（同じく 2026-09-04 追加。3.8 節）。
3. **素子名の重複**（`_dup_msgs`）。
4. **カード内の名前参照**（`directive_ref_check`、2026-09-04 追加）— ディレクティブと
   TEXT フォールバック行の中の `v(ネット)` / `i(素子)` / `@素子[..]` が、図から再抽出した
   デッキの中で解決できるか。検査 2 が**ネット名の全単射**である以上、名前そのものは
   比較されない。しかしシンボルの無い素子は `.asc` の中でネットを**文字列で**指しており、
   図の側でその名前が消えれば回路は壊れる。入力デッキ側でも同じ参照が宙に浮いている場合は
   FAIL ではなく NOTE にする（入力そのものの性質であって、変換が壊したものではないため）。
5. **ディレクティブ集合の照合**（`directive_set_check`、2026-09-04 追加）— `.asc` が
   TEXT `!` として運んでいる `.xxx` カードの**多重集合**が、入力デッキのそれと一致するか。
   削除も追加も FAIL。3.8 節に「何を内容で比べ、何を比べないか」の理由を書いた。
6. **抽出器のエラー**（`_extractor_errors`、2026-09-04 追加）— `asc2ngspice.py` が
   `.asc` の中に**ネットリストへ運びようのないもの**（未知の `SYMATTR` など）を見つけた場合、
   その先のラウンドトリップは「図の一部が黙って欠けたデッキ」との比較になる。
   支えられない PASS を出すより FAIL する。

**#7 を FAIL に格上げした理由**（どちらの選択もあり得るので明記する）:

- `ngspice -b` は素子名が重複したデッキを **実行せずに拒否する**
  （`Error on line 4 ...: device already exists, bail out`。`audit_fable/dup_test.cir` で実測）。
  つまり入力そのものが誰にもシミュレートできないデッキである。
- `topology()` は素子名をキーにするので、2 枚目のカードが 1 枚目を**上書きする**。
  重複があると素子が 1 つ黙って比較から落ちる（`dup_test` は 4 素子中 3 素子しか
  比較されていなかった）。`VERIFY: PASS` の隣に NOTE を出すのは、
  **実在しない検査カバレッジを主張していた**ことになる。
- このリポジトリのどのデッキにも重複は無い（10 デッキで実測 0 件）ので、
  格上げによって既存の PASS が FAIL に変わることはない＝純粋に厳しくなっただけ。

### 3.6 2026-08-27 の独立監査と、その結果入れた修正

証拠一式は `ngspice/audit_fable/`（監査者が作った破壊済み `.asc` と、
独立実装の union-find `ltspice_contact.py`）。修正前のツールは
`asc2ngspice.py.pre_audit_fix` として残してある。

**指摘 1 — `--check` が LTspice の接触意味論を実装していなかった。**
`check_only()` はラウンドトリップしか回しておらず、`geometric_check()` を
**一度も呼んでいなかった**。そのラウンドトリップの再抽出器 `asc2ngspice.py` は
(a) 配線の端点同士 (b) 配線の上に乗ったシンボルピン しか union しておらず、
**配線の途中に着地した端点（T 分岐）**と**配線の途中に置かれた FLAG** を見ていなかった。
5.5 節が「この安全網はラウンドトリップより厳しい」と書いていたとおりで、
**安全網の方が基準より強い**という逆立ちした状態だった。

修正（両方入れた）:

- `asc2ngspice.py` の netlister に不足していた union を追加した。
  配線端点・シンボルピン・FLAG のすべてを「関心点」とし、**配線の線分上に乗って
  いれば内部でも union する**。
- あわせて**ネットラベルの大域性**を明示的に実装した。同名 FLAG の連結成分同士を
  union する。これにより、1 つの連結成分が 2 つの名前を持つ場合（＝ 中途 FLAG や
  T 分岐による短絡）に、その 2 つのネットが**同一ノードとして出力される**ようになり、
  ラウンドトリップのトポロジー比較が破損を見られるようになった。
  該当時はデッキ先頭に `* WARNING: these net labels are ELECTRICALLY THE SAME NODE` を出す。
- `net2asc.py` に `asc_contact_check()` を追加し、`--check` と生成時検証の両方で
  **`.asc` の図形に直接**接触解析を掛けるようにした（3.5 節の検査 1）。

**指摘 2(a) — ngspice のノード名は大文字小文字を区別しないが `parse_cir()` は区別していた。**
`audit_fable/case_test.cir` は `N1` と `n1` を同じノードとして使う。実測で
`ngspice -b` は `v(n1) = 3.333333e+00` の 1 ノードとして解くのに、修正前の
`net2asc.py` は**繋がっていない 2 つの島**として描き、しかも `VERIFY: PASS` を返していた。

修正: `parse_cir()` がノード名を **最初に現れた綴りに揃える**。同一性は
大文字小文字無視、**表示（FLAG のテキスト・ラベル）は作者の綴りのまま**で、
図を小文字化はしない。実際に 2 綴り以上が畳まれたときは
`NOTE: net-name spellings ['N1', 'n1'] are ONE node in ngspice ...` を必ず出す。

これに伴い、`asc2ngspice.py` が無名ジャンクションに付ける自動名 `n1`, `n2`, … が
**そのファイルの FLAG 名と衝突しない**ようにした（大文字小文字無視で回避）。
5B.6 に書いてあった衝突の危険を、回避策（全ネットにラベルを振る）ではなく
発生源で潰したもの。既存 8 枚の `.asc` の抽出結果は 1 バイトも変わらない。

**指摘 2(b) — `compare_topology()` が素子の値を比較していなかった。**
`audit_fable/corrupt_C_value.asc`（`L1` の `SYMATTR Value` を `{L}` → `1e9`、
すなわち 1 GH のインダクタ）が PASS していた。

修正: `normalise_value()` を通して値を比較する。**適用した正規化はこの 4 つだけ**:

1. 値と X 呼び出しのインスタンスパラメータを連結する（`parse_cir` が分離し、
   `asc2ngspice.py` は 1 つの尾部として再生成するため）;
2. 連続する空白を 1 個に畳み、前後を strip する
   （このリポジトリのデッキは `D1      0     N1   DRBE01VYM6A` のように桁揃えしている）;
3. `=` の周りの空白を除去する（`Rser = 6.24m` == `Rser=6.24m`）;
4. ngspice の `'expr'` を LTspice の `{expr}` に書き換える
   （`.param` カードに対して `_to_braces()` が既に行っている変換と同じで、
   ngspice にとって両者は同義）。

**適用していない**もの: 大文字小文字の畳み込み（モデル名はノード名ではない）、
数値の再整形（`1e9` を `1G` と同一視することはしない）、単位の除去。

**明示的な除外は 1 件だけ**: 入力カードに値が無く、再抽出器が既定モデル名
（`D` / `SW` / `NMOS` / `PMOS`）を**発明した**場合。これは MISMATCH ではなく NOTE。

なお `asc2ngspice.py` は LTspice の `Rser` / `Lser` を明示的な直列 R / L に展開するので
ラウンドトリップ側に `Rser_L1` のような**素子が増える**。これは値比較ではなく
既存の「素子名集合の一致」検査が拾う（`elements EXTRA in round-trip deck`）ので、
値比較が偽陽性を出すことはない。`Rser` を 9 個持つ `improved.asc` を自分自身の
抽出結果に対して `--check` した結果は、50 素子で偽陽性 0・`VERIFY: PASS`。

### 3.7 2026-09-04 の独立監査と、その結果入れた修正

2 回目の独立監査。「工学的な中身は妥当だが、この状態では引き渡せない」という判定で、
**素通りする改竄が新たに 2 種類**見つかった。両方とも塞いだ。

#### (A) 1 本のネットを一貫改名すると素通りした

`buck_sync.asc` の `sw` の FLAG **2 枚とも** `swzz` に書き換えると `VERIFY: PASS`・
終了コード 0 になった。照合はネット名の**全単射**なので、改名そのものは（正しく）
差分にならない。しかし壊れているのは図の外である:

```
Bihs nihs 0 V = ((v(ghd)-v(sw))   > {VGMID}) ? i(vlsense) : 0
```

`Bihs` / `Bils` / `Bdt` はシンボルが無いので**図に描かれず**、`!` ディレクティブとして
`.asc` に入る。そこではネットを**名前の文字列で**指しているので、図の側の `sw` が消えると
この参照は宙に浮き、ngspice は浮いた新しいノードを作ってモニタが 0 を返す。
＝**回路は壊れているのに PASS**。

対策 = 検査 4（`directive_ref_check`）。再抽出したデッキのすべてのカード
（素子カードの生テキスト・ディレクティブ・`K` 文）の中の
`v(ネット)` / `i(素子)` / `@素子[..]` を集め、そのデッキ自身で解決できるか見る。
解決できないものは

```
DANGLING NET REFERENCE: a card carried into the .asc names net 'sw' by text,
but no net of that name exists in the drawing (it does exist in buck_sync.cir).
```

として FAIL。**入力デッキ側でも同じ参照が解決できない場合は NOTE に落とす** ——
それは入力そのものの性質であって、この道具が壊したものではないから。
負の対照実験 `tests/corrupt_D_netrename.asc` を追加した。

#### (B) `.asy` の `PINATTR SpiceOrder` を読んでいなかった

`load_asy()` は `PIN` 行の**ファイル順**を端子順として使い、それが `SpiceOrder` と
等しいことを*仮定*していた（旧 docstring に「Pin order per symbol == SpiceOrder ==
file order」と書いてあった）。同梱の 10 シンボルはすべて一致しているので**実害は無かった**が、
`PIN` ブロックの順序が `SpiceOrder` と食い違う `.asy` は LTspice 的には**合法**である。

監査は `voltage.asy` の 2 つの `PIN` ブロックを入れ替えて（`SpiceOrder 2` が先、`1` が後）
これを実証した。旧実装では生成側（`net2asc.py`）と抽出側（`asc2ngspice.py`）が**同じ**
間違いをするので、ラウンドトリップは PASS する。しかし出来た `.asc` を正しい
`SpiceOrder` で読むと **全電圧源の極性が反転**していた:

```
旧ツール + 改竄 voltage.asy が生成した .asc を、正しい .asy で抽出:
    Vsrc 0 n12 DC {Vin_dc}      ← 48 V が -48 V になる
    Vgh  sw ghd PULSE(...)      ← ゲート駆動も反転
```

対策: `PINATTR SpiceOrder` を読み、その値で `PIN` を並べ替える。

- `SpiceOrder` があればそれを使う（LTspice と同じ）
- 無ければファイル順に落とし、**NOTE**（＝これは推定であると明言する）
- ファイル順と食い違えば **WARNING** を出したうえで `SpiceOrder` を採る
- `SpiceOrder` の値が重複していて使えなければ **WARNING** ＋ファイル順

同じ改竄 `voltage.asy` で再実行すると

```
WARNING: voltage.asy: PIN file order and PINATTR SpiceOrder disagree
  (SpiceOrder of the PIN lines, in file order, is [2, 1]); using SpiceOrder
  -- that is what LTspice netlists
```

が出て、生成された `.asc` は**改竄前と 1 バイト差もなく同一**になる。
同梱シンボルは元から一致しているため、5 デッキの `.asc` はこの修正の前後で
**バイト一致**（＝挙動の後退は無い）。

#### (C) 同時に直した配布物の衛生

- 絶対パス（ユーザー名・ディレクトリ構成）をパッケージ全体から除去。
  `examples/buck_sync.cir` の `.include` は**同梱していないライブラリ**への
  相対パス・プレースホルダにし、その旨をファイル冒頭と README に明記した。
- zip に入っていた `tools/ltsym/Misc\jumper.asy`（文字としてのバックスラッシュを含む
  ファイル名。`Misc/jumper.asy` の重複で、Windows 展開時に衝突しうる）を削除。
  `jumper` シンボルは `Misc/jumper.asy` から従来どおり解決される
  （`jumper` を使う手描き `.asc` の抽出結果が従来と一致することで確認）。
- `tests/corrupt_*_rt.cir` を削除。あれはラウンドトリップの**副産物**であって入力ではなく、
  しかも `selftest.sh` を走らせるたびに `tests/` に書き戻されていた。
  `selftest.sh` が `--rt` を作業ディレクトリに向けるようにして、
  **セルフテストがパッケージを汚さない**ようにした。
- 未定義パラメータを**標準出力にも**出すようにした（`undefined params: ...`）。
  以前は生成された `.asc` の中の TEXT にしか無く、標準出力だけを読む使い方では
  見落とすようになっていた。

### 3.8 2026-09-04 の独立**再**監査（3 回目）で見つかった 3 つの穴

証拠一式は `ngspice/audit_fable3/`（監査者が作った `atk1`〜`atk10`）。
前回の指摘は「本当に直っている」と確認されたうえで、**新しく 3 つ**見つかった。

| B3 | `!.tran` カードを削除 / `!.ic v(mid)=2` を削除 | **走らない／初期状態が違う**のに PASS |

**B1 — `SpiceLine` の未消費キーと `Value2` を黙って捨てていた。**
`asc2ngspice.py` の `parse_spiceline()` は `rser`/`lser` だけを取り出し
（それは正しく明示素子へ展開していた）、**残りのキーを一つ残らず捨てて**いた。
`SYMATTR Value2` に至っては**一度も読んでいなかった**。
LTspice が実際にネットリストへ書き出すのは

```
<素子名> <ノード…> <Value> <Value2> <SpiceLine> <SpiceLine2>
```

なので、捨てた部分はそのまま「図には有るがデッキには無い回路」になる。
ラウンドトリップの比較対象に出てこない以上、検査は原理的に見られなかった。

修正の形は「`Rpar` を知る」ではなく「**何も黙って捨てない**」:

- 消費しなかった `SpiceLine` のキー（と `Value2` / `SpiceLine2`）を
  **そのまま素子カードの尾部に付ける**（`spiceline_leftover()` / `_card_tail()`）。
  こうすると値比較がそのまま拾う。付けたときは WARNING を出す
  （LTspice は解釈するが ngspice が解釈するとは限らないため）。
- それでも置き場所の無い `SYMATTR`（`SpiceModel` など、`KNOWN_SYMATTR` に無いもの）は
  **ERROR にして落とす**。`asc2ngspice.py` 単体でも終了コード 1 になる。

  > **なぜ捨てずに落とすのか。** 属性を捨てた抽出器の出力と入力デッキを比べても、
  > 「一致した」は「その属性が無害だった」ことの証拠にならない。
  > 比較できないものを黙って比較対象から外すのは、**存在しない検査カバレッジを
  > 主張する**ことであり、この文書が #7（素子名の重複）で一度通った道と同じ。

  `rser`/`lser` の展開は従来どおり動く（`improved.asc` の 9 本の
  `SYMATTR SpiceLine Rser=...` で確認。抽出結果は**1 バイトも変わらない**）。

**B2 — `K` の結合係数を比較していなかった。**
`topology()` が `kmap[t[0]] = t[1:-1]` と書いており、**最後のトークン＝結合係数を
意図的に捨てて**、結合する相手だけを比べていた。相手の入れ替えと `K` カードの削除は
落ちていたので、表の #9 は「する」と書けていた——が、**値だけは通っていた**。
修正: `k_parts()` で名前・相手・係数に分け、係数を `normalise_value()` に通して比較する
（素子値とまったく同じ正規化）。braces 内に空白がある係数（`{k * 2}`）にも対応した。

**B3 — ディレクティブの存在を比較していなかった。**
`.tran` カードや `.ic` カードを `.asc` から消しても素通りした。
文書化されていた除外は「`.model`/`.param`/`.options` の**中身**は比べない」であって、
**`.ic`/`.tran` の削除**を許すとは書いていない。実装のほうが文書より緩かった。

修正: `directive_set_check()` を追加した。**何をどう比べるかは意識的に選んである**:

| ディレクティブの種類 | 比べ方 | 理由 |
|---|---|---|
| `.xxx` カードすべて（`.tran` / `.ic` / `.nodeset` / `.model` / `.param` / `.options` / `.meas` / `.include` …） | **内容**（多重集合、`normalise_value()` 正規化） | `net2asc.py` はディレクティブを `.asc` へ**逐語的に**写す。唯一の書き換えは `.param` への `_to_braces()` で、`normalise_value()` が両側に同じ `'expr'`→`{expr}` 変換を掛けるので、ここでの内容比較は近似ではなく厳密。5 デッキで実測（37 / 39 / 42 / 46 / 3 カード）して多重集合が一致することを確認したうえで採用した |
| `K` カード | **比べない（ここでは）** | ドットカードではないうえ、検査 2 の `kmap` が相手と係数の両方を比べている。二重に落とすとメッセージが 2 つ出るだけで情報が増えない |
| シンボルの無い素子カード（`B`/`E`/`G`/`F`/`H`） | **比べない（ここでは）** | `topology()` が**素子として**値まで比べている（削除は「素子が欠けた」、改変は VALUE 不一致で落ちる） |
| `;` の TEXT 行（表題・注記・未定義パラメータの雛形） | **比べない** | ディレクティブではなく、シミュレーションに影響しない |

比較は**多重集合**なので、同一のカードが 2 枚あってその片方を消しても落ちる。
削除も追加も FAIL する。

正規化は `normalise_value()`（素子値とまったく同じもの）に加えて、
**先頭の `.キーワード`だけ**を小文字化する。SPICE のディレクティブ名は
大小文字を区別せず（`.TRAN` と `.tran` は同じカード）、`asc2ngspice.py` 自身が
翻訳後の `.tran` を小文字で書き出すため。**本体は畳まない**（モデル名はキーワードではない）。

#### 入力デッキが `asc2ngspice.py` の生成物である場合（2026-09-05、`audit_fable4`）

上の逐語比較が成り立つのは、**入力デッキが人の書いた `.cir` で、`.asc` はそこから
`net2asc.py` が描いた図**という向きに限る。ディレクティブが逐語で写るのはこの向きだけである。

逆向き――**`.asc` と、その `.asc` から `asc2ngspice.py` が作ったデッキ**――では逐語ではない。
`emit()` は次の書き換えを行う：

| `.asc` 側 | 生成デッキ側 |
|---|---|
| `.param a1=10 b1=1 c1=a1/b1`（1カード） | `.param a1=10` / `.param b1=1` / `.param c1=a1/b1`（3カード） |
| `.param η=0.85` | `.param eta=0.85`（ギリシャ文字の音訳） |
| `.tran 0 4m 0 20n startup` | `.tran 20n 4m 0 20n uic`（`startup`→`uic`、Tstep=0 を Tmax で埋める） |
| （無し） | `.param pi=3.14159265358979`（注入） |
| （無し） | `.options itl4=1000 trtol=100` 等の収束補助（注入） |

そのため逐語比較では**無傷の図面が FAIL した**。PSFB の3図面で実測すると、
`compare_topology()` は素子52個・ネット32本で完全一致（MISMATCH ゼロ）なのに、
`directive_set_check()` だけが 30 件の MISSING / ADDED を出していた。
読み手にはこれは「図面が壊れている」としか読めない。
**常に FAIL する検査は、いずれ読み飛ばされる**——偽陽性は偽陰性と同じ理由で危険である。

修正（2026-09-05）: 入力デッキが `asc2ngspice.py` の生成物である場合に**限って**、
比較の両辺を**同じ翻訳器に通す**。すなわち、`.asc` が運ぶ生のカードではなく、
`check_only()` が既に書いているラウンドトリップ・デッキのカードを入力デッキと比べる。
書き換えは両辺に等しくかかって相殺し、注入されたカードは両辺に等しく現れ、
順序は多重集合なので無関係になる。

判定はデッキ先頭の provenance 行 `* generated by asc2ngspice.py from ...` で行う
（`deck_is_a2n_generated()`。先頭のコメントブロックだけを見る）。書き換えはカード自身には
痕跡を残さないので、これ以外に見分ける手がかりはない。
**人が書いたデッキ相手の逐語比較は一行も変えていない。**

検出力は落ちていない。`tests/a2n_dir_test.cir` を使ったセルフテストの 2c で、
生成デッキ相手でも `.tran` の削除・複数代入 `.param` からの1代入削除・パラメータ値の改変・
カードの追加がすべて FAIL・exit 1 になることを、**メッセージまで**照合している。
複数代入カードの1代入だけを消す改竄については、逐語比較よりむしろ**分解能が上がっている**
（カード全体の MISSING+ADDED の対ではなく、`.param spare=3` が消えたと名指しで出る）。

#### 非ASCII の綴り —— 走らないデッキを PASS と言っていた（2026-09-05、穴 E1）

`emit()` は `.param` の名前と式、および `.model`/`.options` 等のカードに対して
`η`→`eta` の音訳を掛けていた。**素子値は掛けていなかった。**

```
.param eta=0.85          ← 定義：音訳された
R1 in mid {1k*η}         ← 参照：音訳されていない
```

ngspice-41 はこれを `Undefined parameter [__]` / `Cannot compute substitute` で
**fatal error** にする。ところが `net2asc.py --check` は **PASS** を返していた。
理由は明快で、比較しているのは「入力デッキ」と「同じ `emit()` が作ったラウンドトリップ・
デッキ」であり、**両辺が同じ未翻訳の文字列を運ぶ**ので差として出ようがない。
これは検査の設計上の死角である：**シミュレータが読めるかどうかは、
自分の出力どうしを比べても分からない。**

同時に、倍率接尾辞の実測を取った（ngspice-41）：

| 綴り | 読まれる値 | 出るメッセージ |
|---|---|---|
| `1u` | 1e-6 | — |
| `1µ`（U+00B5 MICRO SIGN） | 1e-6 | — |
| `1μ`（U+03BC GREEK SMALL LETTER MU） | **1.0** | `warning, can't find model '1μ'` |

`1μ` は**警告だけで 10⁶ 倍ずれる**。LTspice は両方 µ として扱うので、
`.asc` の側では見分けがつかない。

修正: `to_ascii_card()` / `ascii_card_check()` を追加し、`emit()` の**最後に
全カードへ一括で**掛ける（コメント行は対象外——表題や日本語注記が入っており、
ngspice は読まない）。音訳するのは**曖昧でない2つだけ**：

- `η` → `eta`（どこでも。識別子の一部にしかなり得ず、接尾辞としての意味を持たない）
- `µ`/`μ` → `u`（**数字か小数点の直後に限る**＝倍率接尾辞の位置。
  識別子の中かもしれない位置では触らない）

それ以外の非ASCII がカードに残ったら、**当てずっぽうで訳さず `ERROR:`** を出す。
`net2asc.py` は `_extractor_errors()` でこれを検査失敗として扱うので、
この種のデッキはもう PASS のまま持ち出せない。

範囲の実測：本プロジェクトの `.asc` 191 本を走査したところ、`µ`/`μ` は**0件**、
`η` は 40 箇所すべてが `!` のディレクティブ（`.param`）の中だった。
**実際に壊れていたデッキは存在しない**——仕掛けられていたが踏んでいなかった罠である。
負の対照は `tests/selftest.sh` の 2d に置いた（`ngspice` が PATH にあれば実機でも読ませる）。

なお、**別バージョンの `asc2ngspice.py`** が作ったデッキ相手では差が出うる
（収束補助の一覧が違えば `.options` が食い違う）。これは誤検出ではない——
その2つのデッキは実際に違うシミュレーションを記述している。

> **重要な注意 1（内容比較の副作用）。** ディレクティブの本体は**文字列**として比べている。
> 単位換算はしない方針（#11 と同じ）なので、`.tran 1u 1m` を LTspice 上で
> `.tran 1000n 1m` と**等価に**書き直すと **FAIL する**。
> 意味は同じでも、この道具はそれを「入力デッキと違うカード」としか言えない。
> 等価判定を勝手に発明するより、落として人間に見せるほうを選んでいる。

> **重要な注意 2（`--check` に渡すべきデッキ）。** `--check` の入力には
> **元のネットリスト**を渡すこと。**ラウンドトリップ生成物（`*_rt.cir`）を渡してはいけない。**
> `asc2ngspice.py` は抽出時に自前のカードを足す——`.param pi=3.14159265358979` と、
> 収束補助の `.options`（`itl4` / `trtol`、5.x 節）——ので、rt デッキを入力にすると
> それらが「`.asc` に無いカード」として正しく報告される。
> これは図の欠陥ではなく、**rt デッキが元のネットリストではない**という事実の指摘である。
> 2026-09-04 の変更以前は rt デッキを入力にしても `VERIFY: PASS` になっていた
> （ディレクティブを一切比べていなかったので当然）。
> `audit_fable3/t_a2/` の `base_rt.cir` / `d_test.cir` は
> どちらも `asc2ngspice.py` の生成物なので、この経路で FAIL するようになった。

**照合先を rt デッキではなく `.asc` にしたのが要点。**
ラウンドトリップ*デッキ*と比べる形にはできなかった。`asc2ngspice.py` は
`.tran` を書き換え（`startup`→`uic`、`tstep` の補正）、`.param` を位相ソートし、
`.options` に収束補助を注入するからである。`.asc` の TEXT を直接見ることで、
**副作用として `.model` / `.param` / `.options` の中身まで比較できるようになった**
（表の #13 が「しない」から「する」に変わったのはこれ）。

## 4. 既知の限界

### 4.1 v1 グリッド（`--layout grid` を明示したときのみ）は可読性を捨てている

> v2b 以降、`--layout auto` で v1 グリッドに落ちるのは **flow も spine も成立しない**
> ときだけになった。テスト 5 デッキではもう 1 つも落ちていない。以下は
> `--v1` を明示した場合の話。


出力は**「ネットラベルのスープ」**である。素子が長方形に並び、それぞれの端子から
短いヒゲが出て、その先にネット名が書いてある、という図になる。

- 電力の流れが図から読み取れない。1 次側・トランス・2 次側・出力フィルタの区別がつかない。
- 同じネット名が図中の離れた場所に何十回も現れる。
- ラベル文字は隣のシンボルの上に重なって表示されることがある
  （**接続には影響しない** — 接続は FLAG の座標と名前だけで決まる）。
- 人間が回路レビューに使う図としては、正直まだ使えない。

**電気的には厳密に正しく、機械的に検証済み**である。そこがこのモードの価値であって、
見た目は価値ではない。

### 4.2 v2 flow レイアウトでも直っていないこと

- **適用範囲が狭い。** 5.2 節の「ハーフブリッジの脚」が見つかるデッキにしか効かない。
  `S`（電圧制御スイッチ）で組んだブリッジ、ダイオードブリッジ、トランスを含む
  絶縁型（LLC / PSFB / 電流ダブラ）はどれも該当しない。
  **v2b 以降、それらは v1 グリッドではなく 5B 章の spine レイアウトが受け持つ。**
  v1 で予告していた「テンプレートマッチ」は今も入っていない。
- **ゲート駆動は配線されない。** 図の下の帯に置かれ、`gh` / `gl` / `sw` / `sgnd` の
  ネットラベルだけで本体と繋がる。ハイサイド駆動が `sw` に浮いている（ブートストラップ
  相当）ことは、帯の左端の `sw` ラベルを追わないと分からない。
- **B/E/G/F/H 制御源は描かれない**（`Bihs` / `Bils` / `Bdt`）。TEXT ディレクティブのまま。
  これらが参照するネット（`v(ghd)` 等）には図中にラベルを立てるようにしたので、
  ラウンドトリップ後のデッキでもノード名は生き残る。
- **電流計として挿入された 0 V 電源が power path 上に 5 個並ぶ**
  （`Vin_am` / `Vdh` / `Vdl` / `Vlsense` / `Vosense`）。値は隠したが、
  シンボルは普通の電圧源と同じ丸なので、一見すると電源が並んでいるように見える。
- **枝が長くなると縦に間延びする。** 分岐の列間隔・段間隔は固定値で、
  文字幅を見て詰める処理は入っていない。ラベル文字同士の重なりは**目視で確認**して
  定数を調整しただけで、自動の衝突判定は入っていない（配線の接触は 5.5 で判定している。
  重なっているのは文字だけで、接続には影響しない）。
- 交差配線のホップ（跨ぎ記号）は描かない。
- ディレクティブの TEXT ブロックが依然としてシートの下半分を占める。
- `.control` ブロックは失われる（2.6 節の通り、意図的）。

### 4.3 両モード共通

- 描けるシンボルは R/C/L/D/V/S と `nmos`（3 端子 `d g s` のサブサーキット呼び出し）。
  `M` / `Q` 素子、`.subckt` 定義の階層展開は未対応。
- `SYMATTR SpiceLine` は X 呼び出しのインスタンスパラメータにのみ使う。
  LTspice の `Rser=` / `Lser=` は**生成しない**（入力 `.cir` に明示的な直列 R/L が
  あればそれは独立した素子として描かれる）。
- ネット名に `[A-Za-z0-9_]` 以外の文字が含まれる場合、`asc2ngspice.py` 側が
  `_` に書き換えるのに対し TEXT で素通しした行は元の綴りのままなので、両者がずれる。
  この場合は警告を出す（黙ってマングルしない）。テスト対象 4 デッキでは該当なし。
- 素子名が重複しているデッキは検出して NOTE を出すが、後勝ちで 1 つに潰れる。
- `X` 呼び出しのノード数は「最初の `p=v` トークンの 1 つ手前がサブサーキット名」という
  ヒューリスティクスで決めている。パラメータを持たない呼び出しでは「最後のトークンが
  サブサーキット名」に戻る。可変長引数の一般解ではない。

## 5. v2 — flow レイアウト（実際に入っているもの）

v1 は「正しさ」を取り、可読性を捨てた。v2 は**正しさを一切落とさずに**可読性を足した。
以下は「やりたいこと」ではなく、`net2asc.py` に実装されて実際に動いているものだけを書く。

### 5.1 直列チェーン縮約

2 端子素子（と MOSFET の D–S）を辺、ネットを頂点とするグラフを作り、
**電力端子がちょうど 2 本しか付いていないネット**を潰して直列チェーンにまとめる。
`0` と、ゲートネット、TEXT カードが名前で参照しているネットは潰さない。

buck デッキでは 27 素子が 13 チェーンになる。例:

```
vin -Lin- dhr -Rlin- dh -Vdh- dhx -XM1- sw      (高圧側の導通経路がまるごと 1 本)
sw  -Vdl- swl -XM2- sgnd                        (低圧側)
sw  -L1- la -Vlsense- lb -Rdcr- vout            (出力フィルタ)
vout -Cout1- co_a -Rcesr- co_b -Lcesl- 0        (出力コンデンサ + ESR + ESL)
```

チェーンは 1 本の直線の「ラン」として描かれる。これが「向きを使う」の実体で、
横向きのランは `R270`（ピン A が左）または `R90`（ピン A が右）、
縦向きは `R0` / `R180` を、**ピンの相対座標から解いて**選ぶ（`_choose_ori()`）。
決め打ちの回転表は持っていない。

### 5.2 ハーフブリッジの脚をグラフから見つける

トポロジー名や素子名では判定しない。次の条件を満たす 2 本のチェーンを探す:

- どちらもちょうど 1 個の MOSFET を含む
- 1 つのネットを共有している
- 上側チェーンはその共有ネットに MOSFET の **ソース**を向けている
- 下側チェーンはその共有ネットに MOSFET の **ドレイン**を向けている

見つかればその共有ネットが**スイッチノード**、上側チェーンの反対端が**上のレール**、
下側チェーンの反対端が**脚の下端**である。buck では `dhx / sw / sgnd` が検出される。

見つからなければ v2 は成立しないと判断して **v1 グリッドにフォールバックする**
（`--layout auto` の既定動作）。LLC / base_diode / improved_s6 の 3 デッキは
スイッチが `S`（電圧制御スイッチ）なので MOSFET が無く、ここで v1 に落ちる。

### 5.3 配置規約

```
   上のレール（入力バス）  ─ 左から右へ ─┐
                                        │
   ┌ 電源 / 入力コンデンサは下に降ろして GND        │
                                        ▼
                                   高圧側 MOSFET   ← ゲートは左にヒゲ + ネットラベル
                                        │
                                     sw ├──── 出力インダクタ → 出力ノード → 負荷 → GND
                                        │            └ 出力コンデンサは下に降ろして GND
                                        ├──── スナバ（縦の枝）
                                   低圧側 MOSFET
                                        │
                                     sgnd ── Lsg ── GND
   ────────────────────────────────────────────
   下の帯: ゲート駆動 / 補助（ネットラベルだけで接続、配線しない）
   ────────────────────────────────────────────
   さらに下: SPICE ディレクティブの TEXT（複数段組）
```

- レールにぶら下がる枝（`0` に落ちるチェーン、下のハブへ行くチェーン）は
  `BRANCH_DX=256` 刻みの列に順に割り当てる。
- 同じ 2 つのハブを結ぶチェーンが複数あるとき（`Lsup` と `Rdmp`）は、
  長い方をレール上に描き、残りをレールの上に平行に迂回させる。
- スナバのような「スイッチノード → 脚の下端」の分岐が脚より長いときは、
  **脚の方を伸ばして**下端の高さを揃える（戻り配線が枝の上を逆走しないように）。
- ネットラベルは必ず**配線の端点**に置く。`asc2ngspice.py` は配線の途中に置かれた
  FLAG を接続として扱わないので、これは正しさの要件であって見た目の話ではない。
  ランの最後の素子のピンにそのままラベルを置くとシンボルの上に文字が乗るので、
  短いスタブを 1 本足してその先に置いている。

### 5.4 MOSFET を描く

`X<name> n1 n2 n3 <SUBCKT> [p=v ...]` のうち、`<SUBCKT>` が

- `SIC_650` / `SR_80`（このプロジェクトのデバイスラッパ）、または
- `.include` されたファイル内で `.subckt NAME d g s`（ポート 3 本、名前が d/g/s）

であるものを `ltsym/nmos.asy` で描く。**ピン順は `.asy` の `PIN` 行順 = SpiceOrder**、
すなわち `D`(1) `G`(2) `S`(3) で、X 呼び出しのノード順とそのまま対応する。

この対応は目視ではなく**ラウンドトリップで検証している**。生成 `.asc` を
`asc2ngspice.py` に通すと

```
XM1 n1 gh sw SR_80 RDSON={RDS1} ...      ← 入力の XM1 dhx gh sw SR_80 ... と一致
```

が出る。D/G/S を取り違えていればネットの全単射が壊れて FAIL になる。

そのために `asc2ngspice.py` に `nmos` / `pmos` の処理を追加した
（InstName が `X` で始まれば `SYMATTR Value` をサブサーキット名、
`SYMATTR SpiceLine` をインスタンスパラメータとして X カードを再生成する。
それ以外なら bulk をソースに繋いだ `M` カードにする）。検証の緩和ではなく、
検証器が新しいシンボルを読めるようにしただけである。

**あわせて `X` 呼び出しのノード数の推定を直した。** v1 は「最後のトークン以外全部がノード」と
していたので、インスタンスパラメータ付きの呼び出しでは `SR_80` も `RDSON={RDS1}` も
ノード扱いになっていた（両側で同じ誤り方をするのでラウンドトリップは通っていたが、
図には描けず、`net names contain characters ...` の警告が出ていた）。
v2 は「最初の `p=v` トークンの 1 つ手前がサブサーキット名」とする。

### 5.5 幾何セルフチェック（v2 で追加した安全網）

配線を引く以上、**引いた線が意図しない場所で接触する**危険が生まれる。そこで
`.asc` を書く前に、自分が出した図形に対して LTspice の接触意味論で union-find を回し、
できた各連結成分が**設計上ただ 1 つのネット名しか含まないこと**を検査する。

union する条件:

- 配線の両端点
- ある配線の端点が別の配線の**線分の途中**に乗っている（T 分岐）
- シンボルのピン / FLAG が配線の上に乗っている

> **2026-08-27 訂正。** ここには以前「このうち T 分岐は `asc2ngspice.py` は見ない。
> つまりこのチェックはラウンドトリップより**厳しい**方向にはみ出している」と書いてあった。
> 事実としてはそのとおりだったが、**それを限界ではなく美点として書いていたのが誤り**である。
> 安全網が基準より強いということは、`--check`（生成しない再検証）にはその強さが
> 一切効いていないということだった（`check_only()` はこの関数を呼んでいなかった）。
> 現在は `asc2ngspice.py` 側に不足していた union を入れて**同じ意味論に揃え**、
> さらに `--check` からも `.asc` の図形に直接接触解析を掛けている。3.5 / 3.6 節を参照。

失敗した場合は `LayoutError` で v1 グリッドにフォールバックする（黙って出さない）。

### 5.6 その他の細かい可読性対策

- `WINDOW` レコードを生成して InstName / Value の位置を明示する。横向きの素子は
  名前を上・値を下に、縦向きの素子は右に縦積みにする。`R180` 系は文字の左右寄せが
  反転するので `Right` 寄せに切り替える。
- 値が `0` の電圧源（電流計として挿入されているもの）は `WINDOW 3 ... 0` で
  **値だけ非表示**にする。属性は残るのでラウンドトリップには影響しない。
- 素子カードの行内コメント（` $ ...` / ` ; ...`）を落とす。v1 はこれを
  `SYMATTR Value` に持ち込んでいたので、シンボルの横に散文が並んでいた。
- SPICE ディレクティブの TEXT は 27 行ごとに段組みする。v1 は 1 段組みで、
  回路図本体の 3 倍の高さを占めていた。
- `SHEET` は実際の内容のバウンディングボックスから算出する。

## 5B. v2b — spine + branches レイアウト（脚が無いデッキの既定）

5 章の flow レイアウトは**ハーフブリッジの脚が見つかるデッキ専用**である。
それ以外は v1 グリッド（ラベルスープ）に落ちていた。v2b はその穴を塞ぐ汎用レイアウト。
`--layout auto` の探索順は **flow → spine → grid**。flow は一切変更していないので、
`buck/buck_sync.cir` は今までどおり脚レイアウトで描かれる。

### 5B.1 背骨（spine）の選び方

5.1 節のチェーン縮約はそのまま使う。チェーンを辺、ネットを頂点とする
**チェーングラフ**の中から、回路の主経路になる**単純パス**を深さ優先で探す
（探索回数に上限を置いた決定的な全探索。列挙順はチェーンの宣言順に固定してあるので、
同じ入力からは必ず同じ図が出る）。

評価値は次の 3 つを優先順に比較する。

1. **パス上の素子数 − スター罰則**
   罰則は「パス上の（`0` 以外の）各ネットについて `max(0, 次数 − 3)`」。
   次数 3 までは中継点として健全（入る・出る・枝が 1 本）で、次数 4 以上は
   「多数の枝を養うレール」なので、そこを背骨が突き抜けるのは避ける。
   `0` は例外（どんな回路でもスターだし、そもそも局所 GND シンボルで描く）。
2. パス上の素子数そのもの。
3. **均質度** — パス上で最も多い素子タイプの割合。繰り返しモチーフ
   （ダイオード梯子、LC ラダー）は人間が主軸に置くものなので、同点なら
   均質なパスを採る。**Dickson ポンプで「ダイオード 6 個」を
   「ダイオード 5 個 + コンデンサ 1 個」より優先しているのはこの項である。**

`0` は**パスの端点にしかなれない**（GND を経由点にした背骨は意味がないため）。
向きは「次数の高いほうの端を左」に固定する。入力レール・帰線は枝が多く、
負荷は 1 本で終端するので、これで概ね「入力 → 出力」が左 → 右になる。

### 5B.2 島（island）ごとに背骨を引く

GND だけで繋がっている 2 つの部分（絶縁型の 1 次側と 2 次側など）はチェーングラフでは
別成分になる。そこで **成分が尽きるまで背骨選択を繰り返し**、島ごとに独立した
水平帯に積む。`llc` / `base_diode` / `improved_s6` はこれで 4〜9 本の背骨に分かれる。

### 5B.3 枝の吊り方

背骨のネットは左から順に処理し、そこに残っているチェーンを 1 本ずつ配線する。
毎回**その場で分類し直す**のがポイント（同じ新ネットへ向かう 2 本目以降は
「新しいハブを作る」ではなく「できたハブへのタップ」になる）。

| 相手 | 描き方 |
|---|---|
| `0` | ハブの真下に**垂直に落として、その枝専用の GND シンボル**で終端。柱が塞がっていれば 192 単位ずつ横にずらす |
| 既存ハブ（同じ段） | その段の**上**に迂回する水平タップ（並列 R/C 枝） |
| 既存ハブ（別の段） | **垂直タップ**。Dickson のポンプ容量が入力レールから段ノードへ降りてくるのはこれ |
| 未配置のネット | 背骨上なら**真上に 1 段上げて新しいレール**にし、そのレールは以後左右に伸びる。レール上なら左（次に右）へ水平に伸ばす |

枝の柱は**取り付け点の x そのもの**なので、繰り返しモチーフは「1 段ごとに 1 本の柱」
として左→右に並ぶ。**モチーフの認識はしていない**（タスクで許容された
「取り付け点順の単純な左→右配置」を実装した）。

### 5B.4 投機配置とロールバック

枝は必ず**投機的に**置く。シート（WIRE / FLAG / SYMBOL / ピン / シンボル外形）を
チェックポイントし、描いてから新しい図形だけを既存の図形と突き合わせる。

- 別ネットの配線同士が 1 点でも触れる
- ピンや FLAG が別ネットの配線の上に載る
- 配線が別シンボルの本体（ピン外接矩形 + 16）を貫く
- シンボル同士が重なる

いずれかに該当したら**巻き戻して次の候補（柱を 1 つ横 / 段を 1 つ上）を試す**。
全候補が駄目なら、そのチェーンだけラベル帯に落ちる（＝ 接続は FLAG が保証する）。
**可読性のために接続保証を緩めることは一切していない。**

### 5B.5 K 結合インダクタ

`K` カードで結ばれたインダクタを含み、両端が同じネットに戻る閉ループチェーン
（GND → 電源 → GND のような 1 次側ループ）は、**相方のピン中心と同じ x** に、
上下 `COUPLE_DY` 刻みで空いている段に置く。左→右の走りと右→左の走りでは
シンボルの向き（`R90` / `R270`）が反転して本体が原点の反対側に出るので、
原点ではなく**ピン中心**で揃えているのが実装上の要点。

### 5B.6 制御端子と自動ネット名の衝突

v2b で 2 つの正しさのバグを潰した。どちらもラウンドトリップ FAIL として観測されたもの。

- **`sw`（電圧制御スイッチ）の NC+ / NC− 端子**が配線されずに浮いていた。
  chain 縮約が制御ネットを通り抜けてしまい、素子ピン側の FLAG と本体側が
  別ネットになっていた。制御端子は**チェーンの端点に固定**し、素子ピンからは
  短いスタブ + FLAG を出すようにした。
- **`asc2ngspice.py` は無名ジャンクションに `n1`, `n2`, … と名前を付ける。**
  デッキ自身が `n1` / `n2` / `N1` … というネット名を持っていると、実在ノードと
  再構成ノードが同じ名前に潰れる（ngspice のノード名は大文字小文字を区別しないので
  `N1` と `n1` も衝突する）。`^[nN]\d+$` 形のネット名を 1 つでも含むデッキでは
  **描画したネットを全部ラベルする**ようにして、自動生成名が一切出ないようにした
  （`rectenna_harvester` / `llc` / `base_diode` / `improved_s6` が該当）。

  > **2026-08-27 追記。** 上は net2asc.py 側の**回避策**であって、
  > 手描きの `.asc` を `asc2ngspice.py` に直接通す場合には効かない。
  > そこで発生源を潰した: `asc2ngspice.py` の自動名は、**そのファイルの FLAG 名と
  > 大文字小文字を無視して衝突しない**番号まで飛ばすようになった
  > （例: `N1`〜`N5` を持つ `rectenna_harvester` では自動名が `n6` から始まる）。
  > リポジトリの 8 枚の `.asc`（`llc` / `improved` / `original` / `sync_ct` /
  > `improved_s6` / `sync_ct_s6` / `buck_sync` / `rectenna_harvester`）を実測したところ、
  > 自動名と FLAG 名の衝突は 1 件も無く、**抽出結果は 1 バイトも変わらない**。

### 5B.7 未定義パラメータの扱い

`{NAME}` を使っているのに `.param NAME=` がどこにも無い場合
（ランナースクリプトが置換する前提のテンプレート）、LTspice はエラーになる。
素子行は**一切書き換えず**、代わりに `.asc` の TEXT ブロックに

```
;=== UNDEFINED PARAMETERS -- THIS SCHEMATIC WILL NOT RUN AS-IS ===
... 説明 ...
;!.param RL_VALUE=<SUPPLY A VALUE>
;!.param TSTOP=<SUPPLY A VALUE>
;!.param K_VALUE=<SUPPLY A VALUE>
;=== end of undefined-parameter note ===
```

を出す。先頭が `;` なので LTspice からはコメントで、`;` を 1 文字消すと
`!` 始まりの SPICE ディレクティブになる。**値は決して捏造しない。**

### 5B.8 spine レイアウトの限界

> **2026-08-28 更新。** 最初の 3 項目は 5C 章で対処した。取り消し線の代わりに
> 「→ 現状」を付記する。**残りの項目は今も限界のまま**である。

- **背骨の選び方はヒューリスティクス**である。5B.1 の 3 項評価は
  Dickson / 出力フィルタのような「明らかな主軸」がある回路ではよく効くが、
  H ブリッジのように高次数ノードが密集した回路では主軸が一意に決まらず、
  結果は「小さな島がいくつも縦に積まれた図」になる（`llc` / `base_diode`）。
  **→ 現状: ブリッジについては 5C.2 の構造テンプレートが背骨探索の前に走るので、
  主軸が一意に決まらない問題そのものを迂回する。テンプレートに一致しない
  高次数ノード密集回路では、この限界はそのまま残っている。**
- **島が縦に積まれるので図が縦長になる。** 島同士を横に並べる処理は入っていない。
  `llc` はシート高さ 7648、`base_diode` は 8000 になる。
  **→ 現状: 5C.1 の棚詰めで解消。`llc` 4752×4272、`base_diode` 5360×4336。**
- **文字の重なりは自動判定していない。** 5B.4 の判定は配線・ピン・シンボル本体だけで、
  `SYMATTR Value` の文字列は対象外。`llc` のゲート駆動まわりでは
  `Cg3` / `Vg3` のラベルが重なる。接続には影響しない。
  **→ 現状: 5C.3 で判定に入れた。推定精度の限界は 5C.3 に明記してある。**
- **K 結合の 2 つのコイルが隣接しないことがある。** 空いている段を上へ探すので、
  先に置かれた並列枝（`rectenna_harvester` の `Rp` / `Cp`）が間に挟まると 2 段離れる。
  x は必ず揃うので「上下に並んだ対」であることは読めるが、
  トランスとして密着してはいない。
- **交差配線のホップは描かない**（flow と同じ）。純粋な交差は接触扱いしていない
  （`geometric_check()` と同じ LTspice 意味論）。
- **ゲート駆動を配線するかどうかがデッキ依存。** MOSFET のゲートネットに触れる
  チェーンはラベル帯に落ちる（flow と同じ）が、`sw` の制御ネットが同時に
  電源端子でもある場合（`Vg1 gc1 A` のような駆動源）は普通の枝として配線される。
  `llc` ではゲート駆動が図に描かれてしまい、その分だけ図が混む。

## 5C. v2c — 島の 2 次元配置 / ブリッジテンプレート / 文字衝突判定

2026-08-28 の独立監査は、v2b が **接続は正しいが読めない図**を出していることを指摘した。
実測での指摘内容:

- `llc` 8 島 / `base_diode` 9 島 / `improved_s6` 7 島 が**縦 1 列**に積まれ、
  シート高さは 6912〜8000。
- **フルブリッジの 4 スイッチが別々の島に散る**（`llc` では S1 / S2 / S3 / S4 が
  4 つの島に分かれていた）。ブリッジもトランスも**構造として見えない**。
  レビューする人は `dcp` / `gc1` / `b` / `A` のラベルを島から島へ追う羽目になる。
- 文字の重なりは文書に書いてあるより多い（`improved_s6` の `gateN4` / `gateP4` が
  スイッチシンボルの上、`xLm2_2` と `Rser_Lm1` が重なる など）。

以下は**実装して動いているもの**だけを書く。3 つとも spine レイアウト側の変更で、
**v2 flow レイアウトは 1 行も触っていない**（`buck/buck_sync.asc` は変更前とバイト一致）。

### 5C.1 島を棚（shelf）に詰める

島は**今までどおり縦 1 列に描く**。これは意図的で、投機配置の検証器
（5B.4）が「すでに確定した図形」だけを見ればよいようにするためである
（新しい帯は必ず全部の下に空いている）。

描き終えてから、**島ごとに剛体として動かす**。そのために `Sheet` は
WIRE / FLAG / SYMBOL / TEXT / ピン / 外形 / 文字箱のすべてに
**どの島が描いたか（`gid`）を記録**している。`translate_group()` が
その島の全レコードを平行移動し、`group_bbox()` が島の外接矩形を返す。

棚詰めそのものは素直な shelf packing（読み順を保ったまま左→右、
入らなければ次の棚へ）。**棚幅は決め打ちではなく探索する**:

```
候補幅 = 最も広い島の幅 … 全島を 1 行に並べた幅   （48 分割）
各候補について実際に棚詰めをシミュレートし、
できあがりの W/H が PAGE_ASPECT (=1.5) に一番近いものを採る
（同点なら面積が小さい方 → さらに候補幅の小さい方）
```

大きさの偏った箱を数個並べる shelf packing の実効効率は
理論値 `sqrt(面積 × アスペクト)` から大きく外れるので、**推定せずに全部試す**方が
確実で、しかも決定的である。

移動量は必ず **16 の倍数**、棚の間隔は `ISLAND_GAP_X=448` / `ISLAND_GAP_Y=384` なので、
**島どうしが接触することはあり得ない**。接続は 1 本も変わらない
（移動後に `geometric_check()` を通して確認している）。

K 結合の相方に合わせて置かれるループ（5B.5）は、**相方の島に所属させる**。
そうしないと棚詰めで相方から引き剥がされる。

島の順序は宣言順だが、**ブリッジのトランスの 2 次側を持つ島だけは
ブリッジの直後に繰り上げる**（`_pack_order()`）。棚に入れば横に、
入らなければ真下に来る。

### 5C.2 構造テンプレート — 4 スイッチブリッジ + K 結合インダクタ対

**入れたテンプレートはこの 1 つだけ**である。`llc` / `base_diode` / `improved_s6`
の 3 デッキを 1 つでカバーできるからで、汎用のテンプレートマッチャは今も無い。

#### 検出条件（`find_bridge()`）

トポロジー名でも素子名でも判定しない。`find_leg()` がハーフブリッジを
**電気的定義**から見つけるのと同じやり方を拡張している
（向きの判定は `leg_orientation_ok()` に切り出して**両者で共有**している）。

1. **スイッチング素子をちょうど 1 個含むチェーン**を集める
   （`sw` シンボル、または 3 端子 `d g s` の MOSFET サブサーキット呼び出し）。
2. その中から**脚**を列挙する: 2 本のチェーンが 1 つのネット（= 中点）を共有し、
   上側チェーンのもう一方の端が `rail`、下側チェーンのもう一方の端が `ret`。
   `rail ≠ ret`、中点は `0` ではない。
   MOSFET を含む場合は `find_leg()` と**同じ向きの条件**を課す
   （上側は中点に**ソース**を、下側は中点に**ドレイン**を向けていること）。
   `S`（電圧制御スイッチ）は 2 つの電力端子が対称なので**向きは要求しない**。
3. **同じ `(rail, ret)` を共有し、中点が異なる脚が 2 本**あること。
4. **2 つの中点が、普通の 2 端子素子の経路でつながっていること。**
   経路は `rail` / `ret` / `0` を経由してはならず、かつ
   **`K` カードに名前の出るインダクタを 1 個以上含む**こと
   （= トランス / 共振タンクの 1 次側）。最短（チェーン数最小）を採る。

同点は `ret == '0'` を優先し、次に 1 次側経路の短い方、
最後にチェーンの宣言順で決める。**すべて決定的**。

一致しなければ `None` を返し、**普通の spine レイアウトがそのまま走る**。
描画途中で `LayoutError` が出た場合もロールバックして spine に落ちる。
**テンプレートが生成失敗の理由になることは無い。**

#### 描き方（`place_bridge()`）

```
   rail  ─────────────┬──────────────────────────┬──────────────
                    [上側]                     [上側]
   mid1 ──(ラベル)────┼──[ 1 次側 / 共振タンク ]──┼────(ラベル)── mid2
                    [下側]                     [下側]
   ret   ─────────────┴──────────────────────────┴──────────────
                                  │
                                 GND（ret が 0 のとき）
```

- 2 本の脚は縦の列。上側チェーンの長さが違っても、**中点の高さ (`mid_y`) は揃える**
  （短い方はレールから配線で伸ばす）。下端 (`ret_y`) も同様に揃える。
- 脚の間隔は「1 次側の走りがちょうど収まる長さ」または `BRIDGE_MIN_DX=1216` の
  大きい方。1216 は、各脚の**横にボディダイオード / Coss の柱が立つ余地**である。
- **中点のネットラベルは外向きのスタブの先に置く。** 中点そのものは
  「上側スイッチ・下側スイッチ・1 次側・スナバ柱」の 4 叉なので、
  そこにラベルを落とすとシンボルの上に乗る。スタブ長は**適応的**に選ぶ
  （スイッチの制御端子ラベルが向きによってどちら側に出るか変わるため、
  文字が衝突しない最初の長さを採る）。
- `ret == '0'` なら下側バスの中央から GND シンボルを 1 つ下ろす。
  そうでなければ `ret` もハブとしてラベルする。

**残りは全部いつもの枝機構に任せる。** ボディダイオード・Coss・スナバは
「2 つのハブ（レールと中点）にまたがる別段のチェーン」なので `vtap` として
**脚の横の柱**に落ちる。これがちょうど人間の描き方と一致する。
供給源・ゲート駆動・2 次側はそれぞれ枝／別の島になる。

あわせて、枝機構に**横オフセット候補**を足した（`branch_up` / `htap` の `off`）。
ブリッジの中点は自分の列を脚に占領されているので、真上に伸ばす候補しか無いと
必ず失敗して島に分裂してしまう。これで `llc` の `Rq1`、`improved_s6` の `Lm2` が
ブリッジの島の中に留まるようになった。

#### 3 デッキで実際に何が検出されたか

| デッキ | 発火 | rail | ret | 中点 | スイッチ | 1 次側（K 結合） |
|---|---|---|---|---|---|---|
| `opt/variants/llc.cir` | **する** | `dcp` | `0` | `A` / `B` | S1, S2, S3, S4 | Cr, Lr, Rwp1, **Lm1** |
| `opt/variants/base_diode.cir` | **する** | `dcp` | `0` | `A` / `B` | S1, S2, S3, S4 | Lr1, Lsx, Rw1, **Lm1** |
| `dist_asc_s6/improved_s6.cir` | **する** | `n4` | `0` | `B` / `A` | S3, S4, S1, S2 | **Lm1**, Rser_Lm1, Ls1, Lr1, Rser_Lr1 |
| `buck/buck_sync.cir` | しない | — | — | — | — | flow レイアウトが先に成立するのでそもそも到達しない |

### 5C.3 文字（TEXT）を衝突判定に入れる

`validate_new()` はこれまで **配線・ピン・FLAG・シンボル本体**しか見ておらず、
属性文字は一切見ていなかった。ここに文字の外接矩形を足した。

#### 何を見るか

| 種類 | 箱の作り方 |
|---|---|
| `SYMATTR InstName` / `Value` | 生成した `WINDOW` レコードを `ORI[ori]` で回して原点を足し、`asc2svg.py` の `text_width()` と `fsize()` で幅と高さを出す。`R90`/`R270` 系は LTspice が文字を中央寄せにするので anchor を `middle` に、鏡像系は Left↔Right を反転（`asc2svg.py` と同じ処理） |
| ネットラベル（FLAG） | 配置中は**保守的に**フラグ点を中心とした箱。図が完成したあとに `refresh_flag_boxes()` が **`asc2svg.py` の `free_side()` をそのまま再実行**して、実際に描かれる側（U/D/R/L）と多段オフセットを反映した箱に**作り直す** |

**メトリックは `asc2svg.py` からインポートしている**（`text_width` / `fsize` /
`BASE_FONT`）。別実装を書くとチェッカとレンダラが食い違うので、
インポートに失敗したときだけ同じ式をインラインでフォールバックする。

判定する組み合わせ:

- 文字 × 文字（属性文字どうし、ラベルどうし、属性文字とラベル）
- 文字 × **シンボルの生のピン外接矩形**（`BODY_PAD` を足す前のもの）

判定**しない**もの:

- **文字と配線の重なり**。回路図では日常茶飯事で、読みやすさを損なわない。
- **下部の SPICE ディレクティブ TEXT ブロック**。図の下に最後に置かれる別物。
- 同じシンボルが持つ自分の InstName と Value の組（設計上ぶつからない位置に置いている）。
- 同じシンボルの文字とその**自分自身**の本体。

シンボル側に**生のピン外接矩形**を使うのが要点である。`BODY_PAD=16` を足した箱は
「配線を通してはいけない範囲」であって、文字の禁止領域ではない。
横向きの抵抗のリード線の 10 単位上にネット名が乗るのは**正常な回路図**であり、
これを衝突と数えると偽陽性だらけになる（実測: `llc` で 23 件 → 5 件に減った）。

#### 失敗したときの扱い（ハードエラーにはしない）

`attempt()` が **2 周する**ようになった。

1. **1 周目（strict）**: 全候補（柱を 1 つ横 / 段を 1 つ上 / …）を、
   **文字を含めた**全条件で試す。
2. **2 周目（relaxed）**: 1 周目が全滅したときだけ走る。
   **文字の条件だけを外して**同じ候補列を試し、最初に通ったものを採用する。
   このとき残った重なりの件数を**数える**。

つまり文字の重なりは「配置をやり直させる理由」ではあっても
「配置を諦める理由」ではない。**接続保証（配線・ピン・FLAG・本体の接触）は
1 周目でも 2 周目でも一切緩めていない。**
2 周目でも駄目なら従来どおりラベル帯に落ちるが、5 デッキでは 1 本も落ちていない。

報告は生成ログの 1 行:

```
  text overlaps (estimated extents): 0 left in the drawing, 0 placement(s) accepted with one
```

左の数字が**完成図に残っている重なりの総数**（`refresh_flag_boxes()` 後の実測）、
右が**文字条件を外して受け入れた配置の数**である。

#### あわせて入れた 2 つの文字対策

- **長い Value の自動段違い（auto-stagger）。** 横向きの走りで、ある素子の
  `Value` 文字列が素子ピッチより広い場合（`PULSE(-5 15 0 {ton} {toff} {pwl} {Tl})` など）、
  1 つおきに Value を 1 行下げる。**配線は 1 本も動かない**（`WINDOW` の y だけ）。
  spine レイアウトのみ（`Sheet.autostagger`）。flow は従来どおり。
- **制御端子スタブを 48 → 96 に伸ばした**（`CTRL_STUB`、spine のみ）。
  `sw` の NC+/NC− から出るヒゲが短く、`gateP3` のようなラベルが
  スイッチ自身の InstName/Value に乗っていた（監査の指摘そのもの）。

#### この判定の限界（重要）

- **推定である。** 実際のグリフ幅はフォント依存で、`asc2svg.py` のメトリックは
  「東アジア文字幅クラスごとの平均 em 数」である。1〜2 文字ぶんはずれ得る。
- **LTspice 本体でどう描かれるかは検証していない**（この環境に LTspice が無い）。
  保証しているのは「`asc2svg.py` の出す SVG と食い違わない」ことだけ。
- **文字と配線の重なりは見ない**（上記のとおり意図的）。
- ディレクティブ TEXT ブロックは対象外。
- ラベルの箱は、配置中は**保守的（大きめ）**、完成後は**実寸**という
  非対称な扱いになっている。したがって「配置をやり直させた重なり」の中には
  実際には重ならなかったものが含まれ得る。**報告している数は完成図の実測**なので、
  過大には出ない。
