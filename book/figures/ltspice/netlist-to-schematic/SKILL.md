# ネットリスト → 回路図（検証つき）

## この skill の前提となる考え方

LTspice の `.asc` は**座標だけのテキストファイル**で、接続情報は書かれていない。接続は座標の一致から創発する。だから：

- 座標を1つ間違えても**構文エラーは出ない**。図もほぼ同じに見える。ネットが静かに切れるだけ
- **LLM に座標を直接書かせてはいけない。** 460行の座標列を頭の中で描画して整合を取る作業になり、誤りは局所的に検出できない

したがってこの skill は「**接続を先に決めて、座標は決定論的コードに計算させ、生成物を機械照合する**」という順序で動く。あなた（モデル）は座標を書かない。

### なぜ「座標だけ」では接続が分からないのか（仕組み）

`.asc` の素子行は、たとえばこうなっている：

```
SYMBOL ind 1264 1264 R270
SYMATTR InstName Lr1
```

ここにあるのは **①どのシンボルか ②配置の原点 ③向き** の3つだけで、
**端子（節点）の座標はどこにも書かれていない。**

端子座標は `.asy`（シンボル定義）から計算する。`ltsym/ind.asy` にはこうある：

```
PIN 16 16 NONE 0        ← ピンA、シンボル内部の相対座標
PINATTR SpiceOrder 1    ← ネットリストで1番目に書く端子
PIN 16 96 NONE 0        ← ピンB
PINATTR SpiceOrder 2
```

この2つを掛け合わせて初めて絶対座標が出る：

```
絶対座標 = 原点 + ORI[向き](相対座標)

ORI = {'R0'  :(x,y)→( x, y),  'R90' :(x,y)→(-y, x),
       'R180':(x,y)→(-x,-y),  'R270':(x,y)→( y,-x),
       'M0'  :(x,y)→(-x, y),  'M90' :(x,y)→( y, x),
       'M180':(x,y)→( x,-y),  'M270':(x,y)→(-y,-x)}
```

上の例なら：
```
ピンA: (1264,1264) + R270(16,16) = (1264,1264)+(16,-16) = (1280,1248)
ピンB: (1264,1264) + R270(16,96) = (1264,1264)+(96,-16) = (1360,1248)
```
＝このインダクタは (1280,1248)–(1360,1248) に横向きに寝ている。

**接続はさらにその先**：全配線の端点を Union-Find で結合し、ピンや FLAG が配線の線分上に
載っていればそれも結合し、できた連結成分が1ノード。FLAG があればその名前、無ければ `n1,n2,…`。

```
.asy（相対座標） ＋ .asc（原点・向き） → 絶対座標 → 幾何的な接触判定 → ネットリスト
```

**この4段目まで行かないと接続は確定しない。** だから：

- **`ltsym/` が無い、または違うバージョンだと、同じ `.asc` でも接続が変わる**
- 向きを1つ間違えると端子が別の場所へ行く（ダイオードなら向きが逆、4端子スイッチなら電力端子と制御端子が入れ替わる）
- 原点を16ずらすと配線から外れて断線する。**構文エラーは出ない**

`PINATTR SpiceOrder` は**ネットリストに書く端子の順番**を決める。`sw`（4端子: A, B, 制御+,
制御−）や `diode`（アノード→カソード）、`voltage`（＋→−）で効いてくる。
ラウンドトリップ照合が**「端子順を保った全単射」**を見ているのは、この取り違えを捕まえるため。

> **このツールは 2026-09-04 から `PINATTR SpiceOrder` を実際に読んでいる。**
> それ以前は `PIN` 行の**ファイル順**を使い、それが SpiceOrder と同じであることを
> *仮定*していただけだった（同梱の10個はたまたま一致しているので実害は無かった）。
> ファイル順と SpiceOrder が食い違う `.asy` は**合法**であり、その場合の旧実装は
> 生成側と抽出側が同じ間違いをするので、電源の極性が全部逆になっていても
> ラウンドトリップは PASS した。現在の挙動：
>
> - `SpiceOrder` があればそれで並べる（LTspice と同じ）
> - `SpiceOrder` が無いシンボルはファイル順に落とし、**NOTE を出す**（＝推定である旨）
> - ファイル順と `SpiceOrder` が食い違う場合は **WARNING を出したうえで SpiceOrder を採る**
>
> 標準出力に `WARNING: <sym>.asy: PIN file order and PINATTR SpiceOrder disagree`
> や `NOTE: ... carry no PINATTR SpiceOrder` が出たら、**そのシンボルの端子順は
> 報告に書くこと。**

- `rectenna_harvester.cir` は未定義パラメータの実例（下記）。

**ツールが見つからない場合は、そこで止まってユーザーに報告する。**

> **絶対にやってはいけないこと：自分で `.asc` を書く／自前の生成器を書く。**
> この skill が存在する理由そのものが「LLM に座標を書かせない」ことにある。
> ツールが無いなら「無い」と言う。代わりに自分で書くのは、この skill の目的を裏切る行為。

## 手順

以下 `TOOLS` は `tools/` の絶対パス、`PY` は python3 とする。

### 1. 生成 ＋ 検証（同時に走る）

```
$PY $TOOLS/net2asc.py <input.cir> -o <out.asc>
```

出力の読み方：

| 行 | 意味 |
|---|---|
| `layout : v2 FLOW` | ハーフブリッジ脚を検出。**最も読みやすい** |
| `layout : v2b SPINE` | 背骨＋枝。鎖状の回路（梯子・整流段）は良好、ブリッジが多いと島に分裂 |
| `layout : v1 GRID` | **フォールバック。配線ゼロのラベルスープ。図としては失格**——ユーザーにそう伝えること |
| `text_fallback` | シンボルの無い素子（B電源・X呼び出し等）。TEXTディレクティブに落ちている＝**図に描かれていない** |
| `VERIFY: PASS` | 接続がラウンドトリップで一致 |
| `VERIFY: FAIL` | **報告して止まる。**「たぶん大丈夫」で先に進まない |

`--layout grid` / `--layout flow` / `--layout spine` で強制指定可。
既存の `.asc` を検査するだけなら `--check <file.asc>`。

### 2. レンダリングして**必ず自分で見る**

```
$PY $TOOLS/asc2svg.py <out.asc> -o <out.svg> --png <out.png>
```

**PNG を画像として読み込んで、実際に目で確認する。** これは省略しない。
過去に「検証 PASS・接続は完璧・しかし部品がバラバラに並んだだけで MOSFET が1つも描かれていない」図を、確認せずに納品しかけたことがある。

見るときの判断基準：**ネットリストを見ずに、電源・主要素子・負荷を識別し、電力経路をたどれるか。**
たどれないなら、たどれないと報告する。「接続は正しい」は図が読めることの代わりにはならない。

#### PNG が作れないとき（`cairosvg` が無い環境）

このツール自体は Python 標準ライブラリだけで動くが、**PNG 変換だけは `cairosvg` に依存する。**
無い環境では `asc2svg.py` は SVG のみを生成し、その旨を表示して終わる。
SVG はテキストなので読めるが、**それは「図を見た」ことにはならない。**

`cairosvg` が無い場合の手順（**この順に、勝手に省略しない**）：

1. `python3 -m pip install cairosvg` が使えるなら入れて、PNG を作って見る。
2. それが不可なら、他の変換手段（`rsvg-convert` / `inkscape` / ブラウザ）が
   その環境にあるか確認し、あれば PNG/PDF にして見る。
3. どれも無いなら、**「目視確認は実施できなかった」と報告に明記する。**
   - 書くこと：「PNG を生成できなかった（`cairosvg` 等が無い）。したがって
     図の可読性は**未確認**である。SVG は `<path>` に出力済み。」
   - **やってはいけないこと**：黙って手順2を飛ばすこと。SVG のテキストを眺めただけで
     「図を確認した」「レイアウトは良好」と書くこと。ユーザーに PNG を渡さずに
     「見やすい図になっています」と主張すること。
4. ユーザーが図を見られる経路（SVG をそのまま渡す等）があるなら、それを提示して
   **判断をユーザーに返す。**

`VERIFY: PASS` は接続の主張であって、図の主張ではない。目視ができなかったなら、
**図についての主張は一切しない**のが正しい報告である。

### 3. 報告

必ず含める：
- `VERIFY` の結果と、素子数・ネット数
- **どのレイアウトが使われたか**（GRID なら図として使えない旨を明示）
- TEXT に落ちた素子があれば、その名前と「図に描かれていない」こと
- 目視の判定：何が読み取れて、何が読み取れないか
- 未定義パラメータがあればその扱い（下記）

## 未定義パラメータ

`{FOO}` を使っていて `.param` が無い場合、LTspice は「Unknown parameter」で開けない。

**まず標準出力に出る**（2026-09-04 追加。それ以前は `.asc` の中の TEXT にしか書かれておらず、
標準出力だけを読むと見落とした）：

```
  undefined params: RL_VALUE, TSTOP, K_VALUE (LTspice will NOT open this as-is; ...)
```

この行が出たら**必ず報告に含める**。そのうえでツールは**素子行に触れず**、
警告ブロックとコメントアウトした `.param` テンプレートを図に埋める：

```
;!.param K_VALUE=<SUPPLY A VALUE>
```

先頭の `;` を消せば有効になる。**値は絶対に勝手に決めない**（物理量を捏造することになる）。ユーザーに提示して埋めてもらう。
`examples/rectenna_harvester.cir` がこのケースの実例。

## 検査が捕まえるもの／捕まえないもの

`NET2ASC.md` に全24クラスの表がある。要点：

**捕まえる**：ネットの取り違え、端子順の入れ替わり（ダイオードの向き・スイッチの制御端子）、配線端点のズレ、線分途中の FLAG、T字接続による短絡、素子名の重複、大文字小文字違いのネット名、
**ディレクティブ／TEXT フォールバック行が文字列で参照しているネット名・素子名が図の中に存在しないこと**（2026-09-04 追加、下記）、
**ディレクティブ（`.tran` / `.ic` / `.model` / `.param` / `.options` …）の削除・追加・中身の書き換え**（2026-09-04 追加）。
さらに、**ngspice が読めない綴りがカードに残っていること**（2026-09-05 追加）——
`η` は `eta` に、倍率接尾辞の `µ`/`μ` は `u` に一貫して直し、
それ以外の非ASCII が残ったカードは `ERROR` にして検査を落とす。
（2026-09-05 まで：`.param η=0.85` は `eta` に直るのに素子値の `{1k*η}` は直らず、
ngspice が `Undefined parameter` で止まるデッキを **PASS** と言っていた。
比較の両辺が同じ未翻訳の文字列を運ぶので、差として出ようがなかった。）

**素子値の改変**も捕まえる。ただしこの一行は 2026-09-04 まで**言い過ぎだった**ので、
何が抜けていたかを書いておく（同日の再監査で見つかった）：

- `SYMATTR SpiceLine` の `Rser`/`Lser` 以外のキー（例：コンデンサへの `Rpar=0.001` ＝
  1 mΩ 並列＝実質短絡）と `SYMATTR Value2`（例：電圧源への `AC 10`）は、
  抽出器が**黙って捨てて**いたため比較対象に出てこず、素通りしていた。
- `K` の**結合係数**（`{K_VALUE}` → `0.001`）も、比較の際に意図的に捨てられていた。
  結合する相手の入れ替えと `K` の削除は落ちていたので、表向きは「捕まえる」に見えていた。

どちらも塞いだので**今は本当に捕まえる**（`tests/corrupt_E`〜`G`）。
一般化すると、**「値を比較している」は「その値が比較器まで届いている」の証拠にならない。**

#### ディレクティブ比較には向きが2つある（2026-09-05 追加）

- **人が書いた `.cir` → `net2asc.py` が描いた `.asc`**（通常の向き）。
  ディレクティブは逐語コピーなので、`.asc` が運ぶカードと入力デッキのカードを
  **逐語の多重集合**で突き合わせる。等価な書き換え（`.tran 1u 1m` ↔ `.tran 1000n 1m`）も
  差として FAIL する。この向きの挙動は 2026-09-05 の修正で**一切変えていない**。
- **`.asc` → `asc2ngspice.py` が作ったデッキ**（逆向き）。こちらは逐語ではない。
  `emit()` が複数代入 `.param` を1カード1代入に分解し、`η` を `eta` に音訳し、
  `.tran ... startup` を `... uic` に書き換え、`.param pi=...` と `.options` 収束補助を
  注入するからである。2026-09-05 まではこの向きで**無傷の図面が FAIL** した
  （PSFB 3図面で偽メッセージ30件。素子52個・ネット32本は完全一致していた）。
  いまは入力デッキが `asc2ngspice.py` 生成物のとき（先頭の
  `* generated by asc2ngspice.py from ...` で判定）だけ、比較の両辺を同じ翻訳器に通す。
  改竄の検出力は落ちていない（`tests/selftest.sh` の 2c が対照）。

**捕まえない**：
- 数値的に等価だが綴りが違う値（`1G` と `1e9`、`1000p` と `1n`）。
  これは**ディレクティブにも同じように効く**——`.tran 1u 1m` を等価な `.tran 1000n 1m` に
  書き直すと、この道具は違いとして **FAIL** する（勝手な等価判定はしない方針）
- **ネット名のリネーム**（後述。1本でも全部でも、条件つきで通る）
- **図の可読性、および回路の電気的妥当性**
- **LTspice で実際に開けるか**——接触規則は仕様からの再実装であり、LTspice 本体と照合したことは一度もない

### ネット名のリネームについて（2026-09-04 に訂正）

以前ここには「**全ネットの一律リネーム**」だけが盲点として書かれていた。**過小評価だった。**
照合はネット名の**全単射**なので、名前そのものは比較対象ではない。したがって
**たった1本のネットを一貫して改名しても、素通りしていた**（`sw` の FLAG 2枚を
`swzz` に書き換えるだけで `VERIFY: PASS`・exit 0 になった）。

2026-09-04 に、**ディレクティブと TEXT フォールバック行の中のネット名を照合するようにした。**
シンボルの無い素子（B/E/G/F/H）は図に描かれず `!` ディレクティブとして `.asc` に入るが、
そこでは `v(sw)` のように**ネットを名前で指している**。図の側で `sw` が消えれば、
その参照は宙に浮く＝回路が壊れる。今はこれを

```
DANGLING NET REFERENCE: a card carried into the .asc names net 'sw' by text,
but no net of that name exists in the drawing
```

として **FAIL** させる（`tests/corrupt_D_netrename.asc` が再発防止の証拠）。
`i(<素子名>)` / `@<素子名>[..]` も同じように素子名を照合する。

**今も捕まえないリネーム**：
- ディレクティブからも TEXT 行からも名前で参照されていないネットの改名
  （＝図の中だけで完結しているネット。電気的には等価なので、これは正しい挙動）
- ネット名を**図とディレクティブの両方で**一貫して書き換えた場合（同上、等価）
- 素子名そのものの改名は別経路で落ちる（照合は素子名をキーにしている）

最後の2点は必ずユーザーに伝える。**「接続が正しい」と「回路が正しい」と「LTspice が開ける」は別々の主張**であり、この skill が保証するのは1つ目だけ。

> 実例：この skill で描いた降圧コンバータは、接続は完全に正しかったが、
> ローサイド MOSFET を毎サイクル アバランシェ降伏させる設計だった。
> **接続の検証では絶対に見つからない。** 見つけたのはエネルギー保存の検算
> （Pin < Pout は物理的にありえない）だった。

   `ngspice` が PATH にあれば、生成デッキを実機に読ませて
   `Undefined parameter` が出ないことまで確認する。
4. **`asc2ngspice.py` が作ったデッキと照合する向き**（`a2n_dir_test.cir`、2026-09-05 追加）で、
   **無傷の `.asc` が PASS** すること（偽 FAIL の再発防止）と、
   それでも `.tran` 削除・複数代入 `.param` から1代入だけ削除・パラメータ値の改変・
   カードの追加が**すべて FAIL** すること。緩めた側の修正なので、
   「緩めたら骨抜きになった」を検出するための対照である。
3. 未定義パラメータが標準出力に出ること
4. 決定論：2回生成して `cmp` でバイト一致

`selftest.sh` は `--rt` を作業ディレクトリに向けているので、走らせても `tests/` は汚れない。

`asc2ngspice.py` を変えた場合は**既存の `.cir` が変わらないこと**も確認する。変わったら「見落としていた接続が見つかった」ということなので、**隠さず数値への影響とともに報告する**（実際に一度起きた：同名 FLAG を結合していなかったため、接地されているノードが浮いて出力されていた）。

## 既知の弱点（ユーザーに先に伝えるべきこと）

- **トランスがトランスとして描かれない。** 一次と二次が別の島になり、結合は `K` ディレクティブを読まないと分からない
- ゲート駆動は島に分かれ、ラベル接続のまま
- テンプレートは「4スイッチブリッジ＋結合インダクタ」1つのみ。ダイオードブリッジ、カレントダブラ、インターリーブ、3レベルは未対応
- 文字の外接矩形は**推定値**で、LTspice の実描画とは照合していない
- 交差配線にホップ記号を描かない
- ディレクティブのテキストブロックがシートの大部分を占める
- 描画対象は R/C/L/D/V/S と3端子サブサーキットのみ。B/E/G/F/H はテキスト行になる

## シェルの注意（実際に踏んだ罠）

- ngspice の `.control` 内の `let` 式で `>` `<` はシェルのリダイレクトとして解釈され、比較が黙って捨てられる。B ソース側に移すこと
- bash で `cmd >/dev/null; echo $(basename $x) : $?` と書くと、**コマンド置換が `$?` をリセットする**。終了コードは先に変数へ取ること
